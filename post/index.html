ocean-post

Statistical validation and analysis toolkit for regional ocean models. Validates model output against multiple observation streams (satellite, Argo, ICES, GLODAP, WOD, tidal gauges), runs scenario analyses, and publishes results as an interactive Hugo website or PDF report.

Bias correction of CMIP6 atmospheric forcing has moved to ocean-prep.

Designed to be model-agnostic — any model that produces NetCDF or Zarr output is supported by describing its coordinate names in a single YAML file. All configuration is layered (CLI flags override per-run YAML which overrides .ocean-post.yaml), so shared settings are declared once and never repeated.

For the full ocean-* toolkit, install via ocean-stack rather than this package alone. ocean-stack sets up all four packages in a single conda environment — the recommended route because xesmf/esmpy, used here for regridding model output onto observation grids, must come from conda-forge and cannot be reliably pip-installed. Use the standalone installation below only if you need this package in isolation.

Part of the ocean-* family: ocean-data · ocean-plot · ocean-prep · ocean-post

Typical workflows

Operational validation loop

run-analyses validations
    ↓  gridded 2D/3D, profiles (Argo/ICES/GLODAP/WOD), tidal, MLE ranking
    ↓  writes analyses/areas/<AREA>/validations/<EXPERIMENT>/
ocean-reporting --hugo /path/to/hugo/   # or --pdf report.pdf

Climate-forcing preparation (bias correction now in ocean-prep)

bc correct      (in ocean-prep — Delta / QM / QDM bias correction of CMIP6 forcing)
    ↓
bc diagnostics  (in ocean-prep — inspect calibration quality)
    ↓
river-projection  (delta-change river flow + nutrient loads)

Automated post-simulation deployment

push-to-remote  (simulation server → analysis server)
    ↓
update-from-remote  (sync + run ocean-reporting + deploy to gh-pages)

Key concepts

  • Area — a geographic domain (e.g. NS, ENA8).
  • Experiment — a named model run within an area (e.g. Baseline, ObsKd).
  • Together area/experiment uniquely identifies every simulation and determines where outputs are written: analyses/areas/<AREA>/validations/<EXPERIMENT>/

Installation

Install the two sibling packages first, then this one:

pip install -e /path/to/ocean-data
pip install -e /path/to/ocean-plot
pip install -e .

Or from the parent directory of all three repos in one go:

for pkg in ocean-data ocean-plot ocean-post; do pip install -e $pkg; done

Quick start

# Run all validation steps for one experiment
run-analyses validations --area NS --experiment Baseline

# Run only one step (e.g. tidal)
run-analyses validations --area NS --experiment Baseline --step tidal

# Generate the Hugo website
ocean-reporting --analyses-dir analyses/ --recursive --hugo /path/to/hugo/

Configuration

Every CLI script loads config from two layers (highest priority wins):

CLI flags  >  per-run YAML (--config ...)  >  .ocean-post.yaml

.ocean-post.yaml in the project root (or ~/.config/ocean-post/ocean-post.yaml for user-wide defaults) holds shared identity declared once per project — not output locations: output.analyses_dir belongs in the per-run config (every run already sets its own; a value here would silently override all of them with one machine-wide location):

metadata:
  author:    "K. Bolding"
  institute: "BB"
  project:   "NorthSea-MFC"
model:
  name:    "pyGETM"

Per-run configs then only need the job-specific parts (area, experiment, variables, observations, model.base_path, etc.). Missing required keys raise a clear error immediately; there are no silent hardcoded fallbacks.

Annotated example configs for every analysis type live in config/.

Tests

pytest       # all tests
pytest -q    # quiet (dots only)

The suite covers coordinate mapping, statistics, layout paths, config utilities, the statistics database, and station reader dispatch. Bias-correction algorithm tests are in ocean-prep/tests/.
