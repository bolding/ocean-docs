Bathymetry Guide

Overview

Two CLIs handle bathymetry:

Command Purpose
bathymetry-regrid Conservative interpolation of a source bathymetry (GEBCO, EMODnet, …) onto a target model grid
bathymetry-create-grid Generate a curvilinear supergrid NetCDF (thalweg-following channel grid)
bathymetry-splice Splice a small, separately-built regional bathymetry patch into a copy of a larger file

bathymetry-regrid

Minimal config

# config/mymodel_bathy_create.yaml

source: /data/GEBCO/GEBCO_2023.nc   # or: emodnet, gebco

grid:
  type: spherical
  lon_min: -8.0
  lon_max:  13.0
  lat_min:  47.5
  lat_max:  62.0
  dlat: 0.05        # dlon computed automatically (equidistant default)

interpolation:
  min_depth: 2.0
  min_wet_fraction: 0.05

smooth:
  rx0: 0.2          # omit to skip smoothing

output:
  file: bathy_mymodel.nc
  report_dir: ./report/mymodel

Running

# Preview resolved paths without running
bathymetry-regrid --config config/mymodel_bathy_create.yaml --dryrun

# Full pipeline
bathymetry-regrid --config config/mymodel_bathy_create.yaml

# Override individual settings on the command line
bathymetry-regrid --config config/mymodel_bathy_create.yaml --smooth-rx0 0.15

Grid types

grid.type Description
spherical Regular lon/lat grid — most common
rotated_pole Rotated-pole curvilinear grid
cartesian Projected (metric) grid
supergrid Load an existing MOM6-style supergrid NC (from bathymetry-create-grid)

Pipeline steps

  1. Build target grid
  2. Read source bathymetry (GEBCO, EMODnet, or user NC)
  3. Conservative regridding (xESMF), or load an existing coarse file (coarse_bathymetry:)
  4. Splice in any raw_patches: (optional — see below)
  5. Apply fixes, set_regions:, interpolation.local_min_depth: (all optional)
  6. Smoothing, thalweg analysis (optional)
  7. Write output NetCDF + Markdown report

raw_patches: regional bathymetry from a better local source

If a better source is available for one region (higher-resolution coastline/ islands, more accurate depths) than for the domain as a whole, build a small patch separately (its own *_bathy_create.yaml + bathymetry-regrid run, a grid: whose lon_min/lat_min/dlon/dlat are chosen to align exactly with the parent domain's own grid — see config/st_malo_bathy_create.yaml for a real, worked example), then reference it by filename in the domain's own config:

raw_patches:
  - name: st_malo
    file: /path/to/bathymetry_st_malo.nc
    # depth_var/mask_var/wet_fraction_var/tolerance all optional, default to
    # depth_raw/ocean_mask/wet_fraction/1e-4

The patch's own raw depth (depth_var, before that patch's own fixes/ masking/smoothing) is spliced into the domain's raw depth before the domain's own fixes:/mask_regions:/analysis:/smooth: run — so those whole-domain-aware stages (rx0 smoothing is a neighboring-cell-pair quantity; basin connectivity/strait detection need the real domain graph) correctly treat the patched region as if it had always been part of the domain, rather than processing it in isolation and stitching the final result on afterward (which is architecturally wrong for exactly those stages — verified in practice: patching raw and reprocessing the whole domain changes cells outside the immediate patch window too, from legitimate whole-domain rx0/connectivity effects).

The output file records what happened, not just the console log: - a raw_patches variable (1=patched/0=unpatched — same flag convention as mask_regions) - a depth_patches variable (the actual spliced-in depth values, NaN outside patched cells — the values counterpart to raw_patches, same pairing as mask_regions/depth_fixes) - a numbered line in the global history attribute, e.g. 1. <timestamp>: raw_patches: applied 'st_malo' from ... before fixes/mask_regions/ analysis/smooth — history in general is a real, numbered list of every major stage the run actually did (raw_patches, fixes, mask_regions, isolated-cell masking, rx0 smoothing), in order, not just this one step.

interpolation.local_min_depth: a stricter depth floor for a smaller area

interpolation.min_depth sets one floor for the whole domain. Some regions need a stricter (higher) floor than that — e.g. a shallow bay or approach channel that regrids to a couple of cells just under a comfortable margin for the model's own numerics, at the grid's coarse resolution — without raising the floor everywhere else in the domain:

interpolation:
  min_depth: 2.0   # domain-wide floor
  local_min_depth:
    - name: st_malo_approach_channel
      bbox: [-2.9, -2.5, 48.55, 48.65]   # [lon_min, lon_max, lat_min, lat_max]
      min_depth: 10.0

This only ever raises an already-wet cell's depth up to min_depth if it's currently shallower — a cell already deeper than the region's floor is left untouched, and land cells are never opened (unlike set_regions:, which forces every cell in its region — wet or dry — to an exact depth). Runs right after set_regions:, before mask_regions:, and raised cells are pinned against later rx0 smoothing the same way set_regions: cells are, so the floor survives to the final output. Recorded in the output the same way as other region-based corrections: a numbered history line (local_min_depth: applied N region(s), M cell(s) raised) and a per-region CSV report (*_04a3_local_min_depth.csv).

Key options

Option Description
--smooth-rx0 VAL Append an rx0 smoothing target (can specify multiple)
--skip-regrid Reload cached raw-regrid result (step 3), skip steps 1–3
--accept-fixes Apply fixes marked applied: true in fixes.yaml
--write-boundaries Write open-boundary T-grid coordinate CSV files
--log-level DEBUG Verbose internal progress

Fixes

The report directory contains fixes.yaml after the first run. Edit entries and set applied: true, then re-run with --accept-fixes to apply them.

# fixes.yaml (generated)
b001:
  lon: 5.3
  lat: 55.7
  action: set_depth
  value: 22.0
  applied: false

bathymetry-create-grid

Generates a thalweg-following curvilinear grid and writes a MOM6-compatible supergrid NetCDF.

Config

# config/mymodel_grid_create.yaml

name: channel_v1

grid:
  type: curvilinear_channel
  centreline:            # list of [lon, lat] waypoints along the channel axis
    - [-4.5, 50.3]
    - [-3.8, 50.8]
    - [-3.2, 51.5]
  nx: 120
  ny: 20
  half_width: 5000.0     # metres, or "auto"

output:
  report_dir: ./report/channel_v1
  supergrid_file: ./grids/channel_v1_supergrid.nc

Running

bathymetry-create-grid --config config/mymodel_grid_create.yaml --dryrun
bathymetry-create-grid --config config/mymodel_grid_create.yaml

The output supergrid NC can then be referenced in a bathymetry-regrid config:

grid:
  type: supergrid
  file: ./grids/channel_v1_supergrid.nc

bathymetry-splice

Splices a small, separately-built regional bathymetry patch into a copy of a larger parent file at the correct index window — the standalone-tool equivalent of raw_patches: above, for merging two already-finished bathymetry files (e.g. to inspect the result of a patch before deciding whether to fold it into a domain's own config) rather than as part of a single bathymetry-regrid run.

# Locate + validate the window, write nothing
bathymetry-splice --parent bathymetry_nse.nc --patch bathymetry_st_malo.nc --check-only

# Splice depth_raw/ocean_mask/wet_fraction into a NEW file (parent untouched)
bathymetry-splice --parent bathymetry_nse.nc --patch bathymetry_st_malo.nc \
    --output bathymetry_nse_with_st_malo.nc \
    --rename bathymetry=depth_raw   # only needed if the parent's own depth
                                     # variable isn't named depth_raw/ocean_mask

--output defaults to <parent stem>_patched.nc; pointing it at the same path as --parent is allowed but never the default. A patch built at the wrong resolution, or one that falls outside the parent's own grid, fails with a clear error rather than silently producing a wrong result.

Prefer raw_patches: (above) over this standalone tool when you also want the domain's own fixes:/mask_regions:/analysis:/smooth: to run on the patched result — bathymetry-splice only merges two already-finished files, it doesn't reprocess anything.
